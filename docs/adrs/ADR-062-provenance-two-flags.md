# ADR-062 — Provenance carries two flags: the AI mark and the licence caveat

- **Status:** Proposed. Freezes on merge to `dev`.
- **Date:** 2026-08-26
- **Issue:** #62 — O-19.1 undischarged: one provenance flag, so Assistant-edited work is told it
  may not be licenseable
- **Decided by:** Architect agent; requires project-owner ratification, see *Open items*
- **Supersedes:** [`ADR-005`](ADR-005-project-data-model.md) in its Provenance part only (§4 of the
  contract, and *Worked example 2*). Every other decision in ADR-005 stands.
- **Contract:** [`docs/specs/project-data-model.md`](../specs/project-data-model.md) §4 — normative;
  this ADR is the reasoning, the contract is the thing that binds.

A bare `§x` below refers to `docs/CORE_DOCUMENT.md`.

## Context

Obligation **O-19.1** ([`docs/specs/function-surface.md`](../specs/function-surface.md) §8) asks for
two flags, and ADR-006 restates it in its own words — *"Provenance needs two flags, not one."*

> **`ai_origin`** (§6.3, the visual mark) on any entity created or materially rewritten by an
> `origin = Assistant` Delta; **`generative_output`** (§6.2, the licence caveat) only on entities
> from `generate_pattern` or `generate_sample`.

Issue #19 closed and PR #36 merged with **one**. `core::Provenance` held `{generated_by,
generated_at}` and everything downstream was derived from `is_human()`, so `src/ui/provenance.cpp`
had a single non-human branch and put the §6.2 sentence in it:

```cpp
return QString("AI-generated by %1 on %2. Music made with it may not be licenseable.")
```

That string reaches the user from four call sites — the Pattern palette tooltip, the Sample row
tooltip, the Sample detail view, and the Arrangement's Placement mark — on **any** Pattern or
Sample the Assistant touched, whatever it did.

### Why one flag is wrong in both directions

**It is not a safe over-warning.** §1.2 is the load-bearing sentence of the project: the user
prompts the individual components and *"the user stays the author."* §3.8 gives the Assistant
complete reach over musical content precisely so it can do ordinary editing — swap an Instrument,
quantise, add a drum lane. Under one flag, a producer who asks the Assistant to tidy a hi-hat lane
is told the result *"may not be licenseable"* — on their own composition, built from stock content
that §6.1 guarantees is safe to release. That is §6.1's promise being retracted for exactly the
users who use the feature the project is built around, and §6.2's own scope — *"AI generation of
individual Patterns and Samples"* — was drawn to avoid it.

**And narrowing the one flag to generative output is equally wrong.** §6.3 tracks AI origin per
Sample and per Pattern, and O-19.1 is explicit that an Assistant-built drum lane *"is AI-authored
and must be marked"*. Dropping the mark on everything else the Assistant makes would trade a false
warning for a missing one.

**§9.4 — *"The product must never present AI-generated content as licenseable"* — is satisfied
either way**, because the caveat still lands on exactly the entities that need it. What one flag
violates is not §9.4; it is the accuracy §6.2 and §6.3 were written to have.

### The second question this ADR has to answer

O-19.1 says both flags are *"set from the `Delta`"*. The merged history contract deliberately
refuses that route. [`history-contract.md`](../specs/history-contract.md) §1 defines Origin as
*"Who caused a Delta: `User` or `Assistant`. **Not the Function's name** — see §7.3"*, because
NON-scope 6 says the user is never shown which Function ran and §7.3 makes the leak
*"unrepresentable, rather than a rule"*. `src/core/ops.h` implements exactly that: `Origin` is a
two-value enum carrying no Function identity. A Delta therefore cannot distinguish
`generate_pattern` from a quantise, and a reader could reasonably conclude the two frozen contracts
contradict each other. They do not, and *Decision 3* records why.

## Decision

### 1. One field with three states, not two booleans

```
Provenance = { authorship: Human | Assistant | GenerativeModel, source: string, at: timestamp }
```

`source` names the model or agent; `at` is a unix timestamp. The two flags O-19.1 names are
**derived predicates**, exactly as §6.3's boolean already was:

| O-19.1 flag | Derivation | Consequence for the user |
|---|---|---|
| `ai_origin` | `authorship != Human` | The §6.3 mark: the corner badge, and the line when the item is opened |
| `generative_output` | `authorship == GenerativeModel` | The §6.2 licence caveat, appended to that line |

Two literal booleans would satisfy the words of O-19.1 and admit a fourth state that means nothing:
`generative_output && !ai_origin` — generative-model output that is not AI in origin. Every reader
and every call site would then carry an unwritten invariant. One field with three states makes the
nonsense state unrepresentable, which is the same move history contract §7.3 makes for Function
names, and it keeps the storage requirement identical to what P5 already demands: the flags are
computed, never stored side by side where they can disagree.

The sets are **nested, not disjoint** — `generative_output ⊂ ai_origin` — and that nesting is the
whole content of the decision. Generated content is marked *and* caveated; Assistant-authored
content is marked only.

### 2. The caveat is worded in one place and reached from one branch

`ui::provenance_text` gains a third case:

| State | Text |
|---|---|
| `Human` | `Made by hand` |
| `Assistant` | `Made with the Assistant (<source>) on <date>.` |
| `GenerativeModel` | `AI-generated by <source> on <date>. Music made with it may not be licenseable.` |

`provenance.h` already promised *"the section 6.2 licence caveat is worded in exactly one place"*.
The caveat is now a translation-unit-local constant in `provenance.cpp`, appended by the
`generative_output` branch alone — so "one place" is structural rather than a habit: no other
translation unit can reach the string, and no other surface can grow a second copy of it.

The mark itself is untouched. `kProvenanceMarkLabel` stays `"AI-generated"` and the badge stays as
merged, for both AI states: §6.3 asks for *one* mark on AI-origin content, not two marks a user
would have to learn to tell apart. The visual design of the mark is out of scope for this issue.

### 3. "Set from the `Delta`" is satisfied by the Function, not by the Delta's `origin`

The history contract already names the way through, at §7.4:

> AI provenance (CD §6.3) is a field in the data model, so setting it is a `Set` Operation. The
> Function **MUST** set it inside the same Delta as the content it marks.

So the rule is:

- `generate_pattern` and `generate_sample` set `authorship = GenerativeModel`. They are the only
  two Functions that may, and they know what they are without being asked.
- Any other Function running under an `Origin::Assistant` Delta that creates or materially rewrites
  a Sample or a Pattern sets `authorship = Assistant`.
- No Function ever *clears* provenance (rule P2), and a Function that neither creates nor
  materially rewrites content writes no `provenance` Edit at all.

O-19.1's "from the `Delta`" is discharged in the sense that matters — the flag is a `Set` inside the
same Delta as the content, so §7.4's undo/redo guarantee holds unchanged — without the Delta ever
carrying a Function name. The two contracts agree; the wording is what looked like a conflict.

**Neither flag is derived from `Delta.origin` at read time.** It cannot be: §6.3 provenance must
survive a save (P1–P3) while the History does not survive a close (history contract §8). Provenance
is stored data that a Delta *sets*; it is never a projection of the History.

## Alternatives rejected

**Two independent booleans on `Provenance`, exactly as O-19.1 words it.** Rejected: it admits
`generative_output && !ai_origin`, a state with no meaning, and turns the nesting into an unwritten
rule enforced at each writing call site. `generate_sample` (#45) and `generate_pattern` (#16) would
each have to remember to set both. The derived predicates keep O-19.1's two names at every reading
call site, which is where the obligation is actually about to be checked.

**Keep one flag and narrow it to generative output.** Rejected: it discards the §6.3 mark on
everything else the Assistant authors, which O-19.1 names in the same sentence (*"is AI-authored and
must be marked"*) and which the palette, the sidebar and the Arrangement already paint. It trades a
false warning for a missing one, and §6.3 asks for the mark unconditionally.

**Keep one flag and reword the caveat to be true of both cases** — e.g. *"parts of this were made
with AI"*. Rejected: §6.2 condition 3 is a specific promise (*"The user is shown a message that what
they produce might not be licenseable"*), and a sentence weak enough to be honest about an Assistant
edit is too weak to discharge it for a generated Sample. One sentence cannot carry two different
truths.

**Derive both flags at read time from the History's Deltas.** Rejected on three counts: the History
is session-scoped and empty after a load (history contract §8), so the marks would vanish on reopen;
§6.3 asks for provenance to be a property of the data model, *"not a one-off warning dialog"*; and
it would break P3 (copies carry provenance) and P4 (undo restores it) at once.

**Put the Function name on the `Delta` so provenance can be derived from `origin`.** Rejected
outright: it is NON-scope 6 and history contract §7.3, and the merged `core::Origin` was built as a
two-value enum specifically to make it unrepresentable. Widening a frozen contract to save one `Set`
Operation is the trade the history contract exists to refuse.

**A fourth state for human-edited AI content.** Rejected: P2 already covers it by omission — an
ordinary edit's Delta contains no `provenance` Edit, so human editing does not launder generated
content (§9.4). A state for it would be a mutation that must touch two things, which P5 forbids.

## Consequences

- **`core::Provenance` changes shape**, and it is a frozen contract, which is why this is an ADR and
  not an edit. `generated_by`/`generated_at` become `source`/`at` — the names spec §4's schema
  already used — and `is_human()` is replaced by `ai_origin()`, so every reading call site now names
  the O-19.1 flag it is actually asking about. Six call sites in `src/ui` moved; nothing changed for
  hand-made or generative content.
- **#45 (`generate_sample`) and #16 (`generate_pattern`) can set both flags when they land**, with
  one constructor: `Provenance::generative_model(source, at)`. They were written against O-19.1 as
  if it were already satisfied, and now it is.
- **Every other Assistant Function acquires an obligation**: create or materially rewrite a Sample
  or a Pattern, and set `Provenance::assistant(source, at)` in the same Delta. This is new work for
  the Function-implementation issues, and it is the §6.3 mark those issues owe.
- **"Materially rewrites" is a judgement, and it is left as one.** `rename_pattern` does not mark;
  `rework_pattern` does. The boundary lives in each Function's definition, where its single effect
  is already stated, rather than in a rule this contract would have to enumerate 43 times.
- **The Assistant line reads *"Made with the Assistant"*, not *"AI-generated"***, so it does not
  claim more than happened. The badge is unchanged, so the user still sees one consistent AI mark
  across both states.
- **O-19.1 is discharged** and marked resolved in `function-surface.md` §8 with a dated pointer
  here, in the style ADR-001 uses for its resolved items.
- **`docs/specs/project-data-model.md` §4 is amended** — new schema, amended P1, new rule P7 for the
  nesting, and a new invariant I11. *Worked example 2* in ADR-005 shows `Generated {...}` in a shape
  that no longer exists; it is corrected there by a pointer rather than rewritten, so the history of
  the decision stays readable.

## Open items — require the project owner

1. **The Assistant line's wording.** *"Made with the Assistant (claude-opus) on 2026-08-26."* is
   this ADR's proposal, chosen to sit opposite *"Made by hand"* and to avoid the word *generated*
   for work the user directed. It is user-facing copy on a §6.1-adjacent surface, and the owner may
   want different words. The split it expresses is the decision; the sentence is not.
2. **Whether `source` on an `Assistant` entity should name the Assistant's model at all.** It is
   consistent with §6.4's *"depends on what generated it, not merely that something did"*, but
   §6.4's reason for that field is the handpicked *generation* model list, which does not apply
   here. Naming the Assistant's model is more information than §6.3 asks for and less than
   NON-scope 6 forbids — it is a model, not a Function — so it is recorded as a choice, not assumed.
